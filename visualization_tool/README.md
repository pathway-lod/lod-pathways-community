# Evidence graph viewer (prototype)

**Try it:** <https://pathway-lod.github.io/lod-pathways-community/visualization_tool/> (open your own Turtle file with
"Open Turtle file"; it stays in your browser).

Shows a **subset** of the evidence RDF of this repository as cards, laid out like slides 24/25 of the
community-call deck. Built for data submitters: what did I upload, which terms are agreed, what is missing.

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # static site in dist/ (base './'; needs any static web server, not file://)
npm run shot -- out.png "data=slide25.nq"   # build + headless screenshot (needs Edge or Chrome)
```

Documentation: [CLAUDE.md](CLAUDE.md) (guide for agents and developers: rules, how to check changes),
[docs/architecture.md](docs/architecture.md) (pipeline, data structures, roles, profile reference, open work),
[docs/layout.md](docs/layout.md) (the layout algorithm), [docs/decisions.md](docs/decisions.md) (why it looks like this), [docs/pmw-structure.md](docs/pmw-structure.md)
(PlantMetWiki structure and clustering options for the global view).

## Design: works for any data that fits the evidence model

The code knows no evidence vocabulary. A **profile** (`public/profiles/*.json`) maps terms to the roles the viewer
uses: which predicates mean *has evidence*, *generated by* and *anchored to*; which classes are claims and runs
(subclasses are followed through the vocabulary shipped with the data, graph `urn:lodviz:vocab`); which namespaces
belong to the knowledge graph or are local placeholders; and how card titles are built. When the ontologies of
PlantMetWiki and of the evidence are fixed, change the profile (and the vocabulary), not the code.
`lod-pathways-draft.json` describes today's `lodp:` draft. With profile *none* the viewer still works on any RDF:
columns by link distance, prefixes taken from the file.

Overlays, each optional: the term table (`terms.json`, from `specification/ontology_terms.csv`) for colours and
requirement badges; a SHACL report (built in by `tools/build_viewer_bundle.py`, or made in the browser with
"Run SHACL validation", see docs/validation.md); pattern checks from the profile
(claim without evidence or anchor, evidence without provenance: only when there is no SHACL report; nodes not
connected to any claim: always).

URL parameters: `?data=<file in public/data>&focus=<claim IRI>&profile=<file or empty>&runs=1&layout=slide&terms=0`.
The header has no profile chooser and no "slide layout" checkbox (removed 2026-11-12, Martin: only one profile for now; decision D29); use `profile=` and `layout=slide` instead.

## What it does

- **Cards, not triples.** One card per resource. Literal values, types and links to resources outside the subset
  become rows. Only links between cards are drawn as edges.
- **Columns by role**, derived from the evidence pattern. Default (compact): runs | data + evidence | claims | PlantMetWiki, so every link goes to a neighbouring column. Slide layout (URL `layout=slide`; no checkbox since 2026-11-12): data | claims | evidence | PlantMetWiki | runs, as on slides 24/25.
  PlantMetWiki cards form trees growing downward (anchor on top, e.g. metabolite → its pathways side by side below).
  The layout is deterministic: claims centred on their evidence, linked claims adjacent, shared data between its
  claims, every edge on its own track, gaps as wide as their labels (see docs/layout.md). In the slide layout,
  edges that skip a column run on a lane above the cards.
- **Row colour = term status**, from `specification/ontology_terms.csv`: reused ontology term, decision open,
  local `lodp:` term, or "not in spec". The badge shows the requirement ID(s).
- **Origin of every triple** (named graph): `generated` = verbatim from the pilot RDF, `plantmetwiki` = PlantMetWiki's
  own RDF, `proposal` = not in the RDF export yet (dashed).
- **SHACL report** (pyshacl, the repo's shapes) on the cards: violations and warnings, and *missing* required
  properties as dashed red rows.
- **Run SHACL validation** for a file without a report: validates the whole file in the browser against the repo's
  shapes (shacl-engine, same results as pyshacl; nothing is uploaded), with progress bar and time estimate; then
  **Save data + report (.nq)**, which reopens with the report. See [docs/validation.md](docs/validation.md).
- **Claims ordered by SHACL problems.** With a report, the Show menu groups the claims: *with SHACL violations*,
  *with SHACL warnings only*, *no SHACL problems* (file order inside), each entry prefixed with its counts (`✕2 !1`).
  The counts are the problems on the nodes of the claim's own view (claim, evidence, runs, data, knowledge-graph
  nodes), so a problem on a shared node such as a run counts for every claim that uses it. "All claims, 100 per page"
  uses the same order, and big files open on the first claim with a violation (else with a warning).
- Click a card to see its RDF (Turtle); Shift-, Ctrl- or Cmd-click adds or removes cards, Shift-drag on the background
  selects a box of cards. The panel shows one combined Turtle of the selection, including the runs shown inside
  selected evidence cards (only the prefixes it uses), which
  **Copy** and **.ttl** export; proposal-only triples are shown below it and not exported.
  Export PNG/SVG of the picture, and **TTL**: the Turtle of everything shown (all subjects of the current view,
  including runs folded into evidence cards; without proposal triples). Open a local `.ttl`/`.nq`/`.trig` file (no report
  then, until "Run SHACL validation"; a saved `.validated.nq` brings its report).
  Files with more than 60 subjects open on the first claim.
- **Global view (test, `global.html`)**: all claims of a file on one Cytoscape.js canvas: knowledge graph in the
  middle, anchors on its rim, claims on an outer ring, unanchored claims in a separate wedge. Click a claim to open
  its cards beside the ring. Experimental: it checks whether Cytoscape.js is fast enough for thousands of claims
  (see docs/decisions.md D21-D22). Default layout since 2026-11-11: the **PlantMetWiki map** (`?layout=kg`): a fixed
  ring of PlantMetWiki groups and pathways that lights up where the file's claims land, claims around it in blocks
  per group, ribbons between them; `?layout=ring` is the earlier anchor ring (D25).

## Data

`public/data/*.nq` and `public/data/terms.json` are built by [`tools/build_viewer_bundle.py`](tools/build_viewer_bundle.py)
(Python, `pip install -r tools/requirements.txt`) from the rest of this repository (`--repo`; default: the
repository root `..`): it cuts a subset (or takes the whole file with `--all`), adds extra Turtle files as
named graphs, validates with the repository's SHACL shapes and vocabulary (pyshacl), and converts its term table.
`bash tools/rebuild_bundles.sh` rebuilds both. Slide 25 is built from:

| File | What |
|---|---|
| `data/slide25/generated_subset.ttl` | written by the script: the claim of feature neg 589 and what it points to, cut out of `shape_constraints/rdf/annotation.ttl` |
| `data/slide25/plantmetwiki.ttl` | PlantMetWiki RDF (CONSTRUCT on the endpoint, 2026-11-10); raw response in `raw_pmw.ttl` |
| `data/slide25/proposal.ttl` | the dashed/grey parts of slide 25, written as RDF; modelling choices marked `CHOICE` |

Example datasets (`public/data/datasets.json`): slide 25 and the repo's sample graph (all four use cases, with SHACL
report), and all four pilots as one plain Turtle file (`all_pilots.ttl`, 4,884 claims, no report: for testing the
global view, big files and "Run SHACL validation" on the Pages site). Other files can be opened with "Open Turtle file" (Turtle; N-Quads, TriG, N-Triples work too).

**Data provenance.** The slide 25 subset (cut from the pilot RDF), the sample graph and the term table in
`public/data/` come from this repository (MIT, `../LICENSE`); `data/slide25/plantmetwiki.ttl` is PlantMetWiki RDF
(endpoint, 2026-11-10).

## Code

| File | Role |
|---|---|
| `src/rdf.js` | vocabulary-free core: parsing (N3.js), index, class hierarchy, subset ("focus"), Turtle of one card |
| `src/profile.js` | everything vocabulary-specific, driven by the profile: roles, titles, term status, pattern checks |
| `src/model.js` | cards, rows, edges; attaching SHACL results and pattern checks |
| `src/ValidationControl.jsx`, `src/validation/` | in-browser SHACL validation: header control, Web Worker, shacl-engine with corrections (docs/validation.md) |
| `src/layout.js` | column layouts (compact / slide; by link distance without claims): claim blocks, linked claims adjacent, KG groups, edge sides |
| `src/CardNode.jsx`, `src/TrackEdge.jsx`, `src/VTrackEdge.jsx`, `src/LaneEdge.jsx`, `src/App.jsx` | ReactFlow rendering (cards, edges on own tracks between columns or between tree rows, edges over the top) |
| `global.html`, `src/Global.jsx`, `src/globalLayout.js` | global view test (Cytoscape.js; deterministic ring layout); reuses `Graph` from `src/App.jsx` for the detail |
| `src/kgStubs.js` | card viewer, selections: stub cards for knowledge-graph anchors the file does not describe (from the snapshot) |
| `src/handoff.js` | hand-off of a selection (and the file text) between global view and card viewer via IndexedDB |
| `src/siblings.js` | global view: links between claims that point at the same node (directly or via evidence) |
| `src/kgMap.js`, `src/kgDraw.js` | global view, PlantMetWiki map layout (test): claim → pathway mapping and geometry; canvas drawing under Cytoscape |
| `tools/build_pmw_snapshot.py`, `tools/pmw_class_groups.csv` | PlantMetWiki snapshot for the map (`public/data/pmw_snapshot.json`); class → group table |
| `tools/build_viewer_bundle.py` | data bundles: subset + SHACL report + vocabulary as N-Quads, term table as JSON |
| `tools/rebuild_bundles.sh` | rebuilds every bundle in `public/data/` and copies the shapes for the browser (`public/data/validation/`) |
| `tools/validate.mjs` | the in-browser validator on the command line (Node ≥ 22), to compare with `shape_constraints/validate.py` |
| `tools/screenshot.mjs` | build, serve, headless screenshots of given URL queries (the visual check) |
