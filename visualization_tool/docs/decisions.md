# Decisions

Dated record of how the viewer got its current form and why. Most were decided with Martin Engst (project owner)
while building the prototype on 2026-11-10. Add new entries at the end; when a decision is reversed, add a new entry
that says so rather than editing the old one.

| # | Date | Decision | Reason |
|---|---|---|---|
| D1 | 2026-11-10 | **Cards, not triples**: one card per resource, literal values as rows inside, only resource-to-resource links as edges | Generic RDF views (force-directed, literals and `rdf:type` as nodes) get "muddy"; the target look is slides 24/25 of the 2026-11-03 community call, which are cards in columns |
| D2 | 2026-11-10 | JavaScript, React + ReactFlow (`@xyflow/react`), N3.js; built with Vite | Martin's suggestion (he uses ReactFlow); easy to embed in a web page later (e.g. the project's specification dashboard) |
| D3 | 2026-11-10 | Always show a **subset**, by default one claim and its neighbourhood | The pilot RDF has ~4,900 claims; a whole-graph view is useless |
| D4 | 2026-11-10 | Audience: **data submitters** first; should also serve any work with PlantMetWiki evidence RDF | Martin: a good view shows people what to upload and where their metadata has gaps |
| D5 | 2026-11-10 | The viewer does **not query PlantMetWiki**; context is fetched once and stored as a file | Martin, for the prototype |
| D6 | 2026-11-10 | First data = **exactly the RDF of slide 25**: generated parts verbatim, PlantMetWiki parts from the endpoint, the slide's dashed/grey parts as a separate `proposal` graph | Martin. The slide itself is hand-made SVG (make_slide_figure_v2.py in lod-pathways-community), so it had to be turned into RDF first |
| D7 | 2026-11-10 | The slide's "Agreement across tools" card has **no link** in the RDF (an orphan) | Martin noticed a link that is not on the slide; it had been a modelling choice of mine |
| D8 | 2026-11-10 | **Vocabulary-free core + profile** (JSON) that maps terms to roles; class hierarchy from the vocabulary shipped with the data; generic fallback without a profile | Martin: the ontologies of PlantMetWiki and of the evidence will be known later; the viewer must work with any data that fits the model, not just the slide |
| D9 | 2026-11-10 | **SHACL report computed beforehand** with pyshacl and shipped in the bundle; no validation in the browser | Most annotation rules are `sh:sparql` constraints, which browser SHACL libraries (rdf-validate-shacl) do not support; pyshacl with the repo's own shapes gives the real results |
| D10 | 2026-11-10 | Bundles as **N-Quads with named graphs** `urn:lodviz:<origin>` | Origin of each triple (generated / PlantMetWiki / proposal) must be visible; N-Quads keeps blank-node labels shared between data and report |
| D11 | 2026-11-10 | Overlays are optional: term table (badges, term status), SHACL report, pattern checks (only without report, except orphans) | The specification is still changing; the viewer must work with any of them missing |
| D12 | 2026-11-10 | **Hand-written deterministic layout**, not force-directed and not (yet) ELK | Predictable pictures that encode the evidence pattern; ELK kept as the option for large subsets |
| D13 | 2026-11-10 | KG (purple) cards that link to each other form a vertical group with the anchor on top | Martin |
| D14 | 2026-11-10 | Claims centred on their evidence cards (block layout), linked claims adjacent | Martin: untangle the edges |
| D15 | 2026-11-10 | **Compact column order is the default**: runs · data + evidence · claims · knowledge graph; slide order kept as an option | Martin's idea: with evidence and data on the left, anchors go straight to the right and KG groups no longer need to sit side by side |
| D16 | 2026-11-10 | Each edge on its own track in the gap; connection points spread along the card side; gap width = widest label | Martin: no overlapping arrows; labels must fit |
| D17 | 2026-11-10 | Data shared by two claims is placed between their blocks | Martin: minimise edge overlaps on slide 25; accepted that with many claims this cannot be solved in general |
| D18 | 2026-11-10 | Own repository, private: github.com/Tontolda/RDF_viewer_prototype | Martin. The bundled team data has no license yet, so it stays private |
| D19 | 2026-11-10 | Only **slide 25 and the sample graph** ship as examples; the full pilot bundles (9.3 MB) and the plain-Turtle copy of the sample graph removed from the menu and the repo | Martin, preparing to host the viewer on GitHub Pages in lod-pathways-community (on a branch). Big files can still be opened with "Open file" |
| D20 | 2026-11-10 | **Moved into lod-pathways-community** as `visualization_tool/` (branch `visualization-tool`), published with the repository's existing GitHub Pages site under `/visualization_tool/` | Martin: other project members should test it with their own data; the repository now has an MIT license, so the example data can be public. One Pages site per repository, so the viewer is added to the existing workflow |
| D21 | 2026-11-10 | Two levels: a **global view** of all claims of a file, and the current cards as the **detail view** opened from it. First sketch: knowledge graph in the middle, claims around it, unanchored data visible separately | Martin: users must see large amounts of data at once; details on demand. "Linked" = the claim has an anchor property in the file; checking anchors against PlantMetWiki is not the viewer's task (other objectives), so D5 stays |
| D22 | 2026-11-10 | Global view test with **Cytoscape.js** (canvas), not ReactFlow and not sigma.js | ReactFlow (DOM) does not scale to thousands of nodes. Cytoscape.js has deterministic preset/concentric layouts, compound nodes for grouping, CSS-like styles, and its JSON opens in Cytoscape desktop, which many biologists know; sigma.js (WebGL) only wins above ~10k nodes (pilots: ~4,800 claims in total) |
| D23 | 2026-11-11 | **Knowledge graph as trees growing downward** (anchor on top at its claim's height, linked KG cards in rows below, side by side, each card centred over its children, the tree shifted so the anchor stays at the KG column); replaces the vertical KG stacks of D13. Trees stacked (compact) or side by side (slide) | Martin: arrows between PlantMetWiki cards all left one point of the border and overlapped (on slide 25 the metabolite → PWY-6684 edge ran behind PWY-2821 and looked like a pathway-to-pathway link). Martin first got a tree growing to the right and chose the downward one; a centred anchor first pushed itself right and widened the gap to the claims beyond the label width, so the tree is now shifted left into the free space of that gap (never past the previous column) Its edges leave the bottom border at spread points and run on their own horizontal tracks (new VTrackEdge; same-column claim links use it too) |
| D24 | 2026-11-11 | **D5 is cancelled** (and the "D5 stays" part of D21): the viewer may use PlantMetWiki content, from a shipped snapshot and/or live SPARQL, e.g. to place the user's anchors inside a simplified PlantMetWiki in the global view | Martin: the global view should show where the user's data lands in PlantMetWiki, which needs a lookup of the anchors. Structure facts and options: [pmw-structure.md](pmw-structure.md) |
| D25 | 2026-11-11 | Global view gets a **PlantMetWiki map** layout (test, default, `?layout=ring` keeps the old one): fixed inner ring of 14 groups / 2,478 pathways from a shipped snapshot, coverage as one purple ramp; all claims stay on the outer ring (clickable), in blocks by primary group; ribbons block → group. Groups = PlantCyc leaf classes sorted into 13 groups by a reviewable table, because PMW has no class hierarchy. Snapshot, not live SPARQL | Martin: users should see how their data maps to PMW and why that is useful; claims must stay visible and selectable. Measured: snapshot 220 kB gzipped; live lookup ~1.3 s for 673 anchors. Hub metabolites (water: 754 pathways) would light up everything, so anchors in >50 pathways do not place a claim and others count 1/n. Built so it can be removed in one step (architecture.md) |
| D26 | 2026-11-11 | **Global view ↔ card viewer**: any pick opens as cards (20 claims per page); the card viewer links back to the global view, which reloads the same data and selection. Hand-off through IndexedDB, not URL parameters | Martin: larger selections must open in the card view, and there must be a way back (reloading is fine). Hundreds of claim IRIs do not fit in a URL, and files opened from disk cannot travel by URL |
| D27 | 2026-11-11 | Selections in the card viewer: **100 claims per page, TTL = whole selection; grid of graphs** (each connected graph laid out on its own, packed in rows); **knowledge-graph stubs** from the snapshot for anchors the file does not describe, plus pathways shared by the view's anchors, so graphs connect through PlantMetWiki. Single-claim views unchanged (no grid, no stubs) | Martin: the card view will mainly be opened from the global view; pages of 20 were too small and the export must cover the whole selection; independent claims should sit side by side, and their relation through PlantMetWiki must be visible ("a grid of graphs, some larger, connected through the link to PMW") |
| D28 | 2026-11-11 | **Multi-select of cards and Turtle export of the selection**: click = one card, Shift/Ctrl/Cmd-click toggles, Shift-drag selects a box (React Flow's selection, synced with App's `selected` list); the panel shows one combined Turtle of the selected cards plus the subjects they show folded in (runs, when runs are not cards); selected subjects first, then their blank nodes, one block per subject, objects of the same predicate grouped (`p o1, o2`), rdf:type first, used prefixes only with Copy and `.ttl` download; triples whose only origin is `proposal` are shown separately and not exported. Backspace no longer deletes cards (`deleteKeyCode={null}`). A **TTL** button next to PNG/SVG exports everything shown (all subjects of the current subset, incl. runs folded into evidence cards; no proposals) | Martin: users need to export a chosen subset as Turtle (a requested feature); proposal triples are not part of the RDF, so they must not end up in an export |
| D29 | 2026-11-12 | **Header slimmed**: profile chooser and "slide layout" checkbox removed from the card viewer header; both stay reachable by URL (`profile=`, `layout=slide`), so the slide layout and the no-profile fallback keep working and stay in the check list | Martin: only one profile for now; cosmetic clean-up of the top panel. Re-add the chooser when a second profile exists |
| D30 | 2026-11-12 | **Gaps widen only where edges run side by side**: track bands of cards whose edges do not overlap in height reuse the same slots; after the y layout, a gap that would put tracks closer than `TRACK_STEP` (12 px) is widened by moving everything right of it (`widenGaps`). Edge shapes stay orthogonal custom edges (ReactFlow's bezier/straight types would drop the own-track routing) | Martin: with many edges on one side the tracks were very crowded; first try (gap ≥ edge count × 12 px) needlessly widened the left gap between evidence and claims, which only has local edges; the right gap to PlantMetWiki, where claims converge, is the one that needs room |
| D31 | 2026-11-12 | **SHACL validation in the browser**: "Run SHACL validation" replaces "no SHACL report"; shacl-engine 1.1.3 (pinned) with three corrections and a speed-up (docs/validation.md), in a Web Worker loaded on the first click; progress bar with time estimate and Cancel; the whole file is validated; **Save = data + report as one N-Quads file** (reopens with the report); shapes copied to `public/data/validation/` by rebuild_bundles.sh, named in the profile | Martin: users should validate their own data on the Pages site and see the violations on the cards, with feedback while it runs, and save the report. Tested alternatives: Pyodide + pyshacl (≈ 10 MB, slow) not needed; stock shacl-engine wrong on our shapes (54/83) and 17 min for the annotation pilot; with the corrections identical to pyshacl on 83 test cases + 4 pilots, 11 s in the browser. Report alone cannot be re-matched to blank nodes after re-parsing, hence data + report |
