# Shape constraints for adding predicted-pathway data to the knowledge graph

SHACL shapes (the W3C standard for validating RDF) and the tools around them, for adding data from **experiments and predictions about pathways** to the PlantMetWiki knowledge graph (KG):

| Case | Data | What is added |
|---|---|---|
| 1 | Predicted biosynthetic gene clusters (plantiSMASH) | BGCs and their links to PlantMetWiki pathways |
| 2 | Paired transcriptomics and metabolomics (MEANtools) | Gene-metabolite associations from functional clusters |
| 3 | MS/MS annotations (GNPS library, SIRIUS, MS2Query, DreaMS, consensus) | Metabolite annotations of LC-MS/MS features |
| 4 | PlantCyc evidence codes on PlantMetWiki nodes | Typed evidence for pathway membership |

The model behind the shapes is described in the [examples](../examples/README.md), with a sample graph that conforms to these shapes.

## Goals

1. **A contract for contributors.** Say exactly what a statement must contain before it can be added to the KG: the evidence, where it came from (tool, version, input data), and which PlantMetWiki node it attaches to.
2. **Catch problems before loading.** Malformed or incomplete data is rejected (*violations*) with a message that says what to fix.
3. **Keep weak support visible instead of hiding or deleting it.** Data that is well formed but weakly supported (an EC number as the only link, a mass-only match, a non-significant cluster, a missing software version) is allowed and flagged (*warnings*), so users can filter it out when they query.
4. **One evidence pattern for all cases**, so a single query can compare predictions of different kinds.
5. **Reproducible RDF.** Generate the RDF from the results of the [pilots](../pilots/) with scripts that build the graphs programmatically, and validate every file they write.
6. **Check references, not only structure.** Test that the PlantMetWiki pathways and metabolites a claim attaches to actually exist (a dated snapshot), which SHACL alone cannot do.

**Not goals.** The shapes do not judge whether a prediction is *true*. They do not load data into the PlantMetWiki triple store, and they do not change PlantMetWiki's own data model.


## The model in one paragraph

Every statement is a **claim** (a node typed as a subclass of `lodp:Claim`). A claim has one or more **evidence nodes** (`sio:SIO_000772`, *has evidence*), each typed with an [ECO](https://www.evidenceontology.org/) class and generated by a **run** (`prov:wasGeneratedBy`) that records the software, its version and the input data. A claim is **anchored** to PlantMetWiki (`lodp:anchoredInPathway` or `lodp:anchoredToMetabolite`), and `lodp:anchorTier` says how strong that anchor is: `curated`, `gene_direct`, `gene_locus`, `structure_match`, `gene_uniprot`, `gene_ec` or `mass_match`, from strongest to weakest. Scores and the case-specific details sit on the evidence node.

## What the shapes check

| Shape (file) | Violations (data is rejected) | Warnings (data is flagged) |
|---|---|---|
| **Claim** (`common`) | has evidence; one anchor tier from the list; anchored in a PlantMetWiki pathway (`PC<n>` IRI) or to a metabolite (InChIKey IRI) | weak anchor (`gene_ec`, `mass_match`) |
| **Evidence** (`common`) | typed with an ECO class; exactly one run, which is a `lodp:Run` | |
| **Run** (`common`) | one software name; at least one input (`prov:used`); at most one version | version missing; no label |
| **Metabolite feature** (`common`) | one feature id and one dataset; ion mode is positive or negative | |
| **Predicted BGC** (`bgc`) | species; evidence; a plantiSMASH 2.0 detection rule (13 allowed values); MIBiG IRI pattern; a match needs its evidence; **exact match means 100% of genes similar, close match less** | prediction not typed with the usual ECO classes or not from a plantiSMASH run |
| **BGC-pathway link** (`bgc`) | overlaps exactly one BGC and one pathway; evidence from a *linking* run; link tier with its matching evidence (genes, proteins or ECs listed); counts at least 1; fractions above 0 and at most 1; anchor tier equals link tier | linking run with fewer than two inputs |
| **Gene-metabolite association** (`association`) | one gene and one feature; Pearson r in [-1, 1]; p-values in [0, 1]; mutual rank at least 1; edge weight in (0, 1]; cluster id and cluster p-value; MEANtools run with a decay rate (5, 10, 25, 50); the anchored side has its tier and the claim's tier is the **weakest** of the sides | functional cluster not significant (p ≥ 0.05) |
| **Metabolite annotation** (`annotation`) | one feature; anchored by `structure_match`; match level stated; `skos:closeMatch`, **never** `exactMatch` (matching the first InChIKey block cannot be exact); every evidence names its tier; ECO class and run type fit the tier; a consensus has match type, a consistent score (full = 1.0, partial = 0.5) and the agreeing tools (3 for full, at least 2 for partial) | a tool evidence without its score |
| **Pathway membership** (`plantcyc`) | subject is a PlantMetWiki node of the same pathway as the object; anchored as `curated`; original `EV-` code; **the ECO class matches the code** (proposed mapping); PubMed IRI pattern | a code with no proposed ECO mapping |
| **Reference check** (`validate.py`) | the pathway or metabolite exists in the PlantMetWiki snapshot | |

Severity belongs to the shape in SHACL, so every warning rule is its own shape. Numeric values must have the right datatype: a probability written as a decimal instead of an `xsd:double` is rejected, because queries would otherwise treat the two differently.

## Run it

```bash
cd shape_constraints
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt     # pinned versions

# validate any RDF file (several can be given; they are validated together)
.venv/bin/python validate.py ../examples/sample_evidence_graph.ttl
.venv/bin/python validate.py rdf/*.ttl --strict                   # warnings also fail

# create the RDF from the pilot results (writes rdf/*.ttl and validates each file)
.venv/bin/python build_rdf.py all
.venv/bin/python build_rdf.py bgc --include-ec                    # also the weak EC-only BGC links
.venv/bin/python build_rdf.py association --max-cluster-p 1.0     # also non-significant clusters

# run the tests (about 20 seconds)
.venv/bin/python -m unittest discover -s tests -v

# update the snapshot of PlantMetWiki's pathways and metabolites
.venv/bin/python refresh_snapshots.py
```

`validate.py` exits with 0 when there are no violations, 1 otherwise (1 for warnings too with `--strict`), so it can run in continuous integration. The builders need the pilots' result files (committed); the annotation builder also downloads the Zenodo S6 tables through the first pilot. The `annotation` case takes about 4 minutes because most of the time goes into the SPARQL consistency checks.

## Results on the pilot data (2026-10)

| Case | Input | RDF | Violations | Warnings |
|---|---|---|---|---|
| 1 BGC | plantiSMASH 2.0 pilot | 57 BGCs, 448 links (direct and UniProt tiers); 7,284 triples | 0 | 0 |
| 2 Association | MEANtools tomato pilot | 1,293 associations from significant clusters (p < 0.05); 26,338 triples | 0 | **1,293** (all weak anchors) |
| 3 Annotation | MS/MS pilot (Brassicaceae) | 2,722 annotations, 3,650 evidence nodes; 54,097 triples | 0 | 5 |
| 4 PlantCyc | PlantMetWiki citations | 364 nodes, 409 evidence entries; 4,207 triples | 0 | 0 |

The sample graph in [`examples/`](../examples/) validates with 0 violations and 1 warning (its cluster is not significant, on purpose).

## What running real data through the shapes showed

- **No MEANtools association is anchored by a strong tier.** All 1,293 carry the weak-anchor warning: 1,081 are anchored only through a mass match, 149 only through an EC number, and 63 through both. This is the pilot's finding, now visible in the data itself.
- **A real data problem was caught.** Four SIRIUS confidence values are `-Infinity` (no confidence computed). The shapes rejected the first export, so the builder now leaves the score out and the shapes flag the missing score as a warning.
- **Unknown software versions show up as warnings.** The GNPS library search has no stated version, which is reported once on its run.
- **Anchoring a metabolite annotation to every pathway of the metabolite is noisy** (glutathione occurs in 106 PlantMetWiki pathway entries). Annotations are therefore anchored to the PlantMetWiki *metabolite*, and pathways are reached through it.
- **The overlap link and the prediction have different evidence.** The BGC is predicted by plantiSMASH, but its link to a pathway is made by our mapping, so the link evidence comes from a separate *linking run* that lists both inputs.
- **Not everything fits the model.** Of the 1,113 PlantMetWiki citation values, only 394 carry an evidence code; the others are plain PubMed lists and are skipped. 30 of those 394 sit on nodes of single-reaction diagrams (`RC…`), which are not PlantCyc pathways and are excluded, as in the pilots. In the association data, 301 pairs in significant clusters are cluster co-members without a direct correlation, so they carry no correlation evidence and are skipped.
- **The draft RDF exports of the pilots do not conform** (for example, no anchor tier and the link attributed to plantiSMASH itself). They are superseded by `build_rdf.py`.

## Decisions to confirm

These are my defaults; each is a one-line change.

- [ ] **SHACL, not ShEx.** pyshacl is used; the SPARQL constraints (consistency rules) are SHACL-SPARQL.
- [ ] **Namespace.** `lodp:` is a placeholder (`example.org`). A permanent namespace is needed before publishing, for example under w3id.org.
- [ ] **Which claims enter the KG.** BGC links of the direct and UniProt tiers only (EC-only links would add 24,000 weak links, 18 MB); associations from significant clusters with at least one anchored side; annotations of all detection tiers (MS2Query analogues excluded, since they are related compounds, not detections). Should weak anchors be loaded at all, or kept in a separate graph?
- [ ] **`skos:closeMatch` for annotations**, with `lodp:matchLevel "connectivity"`. SKOS mapping relations are meant for concepts, not measurements, so a dedicated "annotated as" property would be cleaner.
- [ ] **Functional clusters as attributes** of the association (id and p-value), not as nodes of their own. A cluster node (as a "predicted pathway module" with its genes and metabolites) would avoid repeating the cluster statistics.
- [ ] **PlantCyc curator names are left out** of the RDF; only the evidence code and the PubMed reference are kept.
- [ ] **The ECO mapping of PlantCyc codes** is by meaning. It should be reviewed with the PlantCyc curators (and could be contributed to ECO).
- [ ] **Anchor tier semantics.** `anchorTier` is the weakest tier among the sides used. Is a single value enough, or should every anchor carry its own tier?
